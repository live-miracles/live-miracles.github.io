How Bunryu differs from the tools people usually consider for the same job. It is written for choosing a tool, not for ranking them: each has a case where it is the better pick. Facts about other projects come from their own READMEs, documentation and, where noted, source code, checked in October 2026 against Bunryu 3.0, Restreamer 2.12, SRS 6.0 and MediaMTX 1.21; check their sites for what they offer today.

Why Bunryu exists

We needed one server for dozens of live inputs and hundreds of outputs, and looked at what already existed before writing anything. This is how that went. The code facts (libraries, versions, commit counts) were checked in October 2026; what we saw in our own trials is marked as that, and none of it is a benchmark.

  • Restreamer was the first candidate, and we considered using it. Two things ruled it out:
    • Its built-in SRT server is datarhei's own Go implementation, gosrt (v0.6.0 in Core's go.mod), not Haivision's libsrt. On a flaky network we saw heavy pixelation in streams passing through it that did not appear through libsrt under the same conditions. That was an observation in a trial, not a measurement, and we kept no recording.
    • In our trial the interface did not suit many outputs. Adding an output took many clicks, the output list grew long, and each output's bitrate and health were not shown beside it, so an output with a problem, or one that had restarted, was hard to find. Its UI repository (restreamer-ui) has had one commit since January 2025 and its last release is v1.13.0 (June 2024); the Core engine underneath is more active.
  • MediaMTX has no management UI: it is configured by file and control API. Its SRT is gosrt as well (v0.12.0), so we expected the same weakness. What we measured was its SRT-to-RTMP conversion (see below), not its SRT ingest on its own.
  • SRS uses libsrt, which is mature and widely deployed, and that decided it. Its own console is minimal and its forwarding is static, so around it we built a dashboard and a manager that runs one FFmpeg per destination, so any output starts and stops without touching the others.
  • Paid products such as Wowza, and hosted services such as Restream.io, work, but at our number of inputs and outputs we judged the cost too high to depend on.
  • We found no other open-source restreaming server that combined libsrt, a dashboard and outputs that change while the stream runs.

The result is SRS, libsrt and FFmpeg with about 20,000 lines of TypeScript on top, which manage many inputs and outputs from one place.

Design approach

Bunryu has no media code of its own. SRS accepts RTMP and SRT, libsrt carries SRT (inside SRS and in Goryu), and FFmpeg does everything to the stream after that: the outputs, previews, probing and audio processing. What Bunryu adds is a control plane of about 11,000 lines of TypeScript (38 files, four runtime dependencies), a dashboard of about 8,600 more, and Goryu, about 2,000 lines of C over libsrt.

This is deliberate. Timestamps, codec quirks and damaged input are where media software fails, and FFmpeg and libsrt have long production use on exactly that. In our tests FFmpeg stayed connected through 10% packet loss where a newer converter dropped its readers (details). A small codebase is also easier to read, test and reason about when something fails in the middle of an event.

The cost is efficiency. A copy output is a whole FFmpeg process of about 65 to 90 MB of RAM, where a purpose-built forwarding hub used about 10x less RAM, though about 1.5x more CPU (details). That is acceptable inside the supported capacity, and we chose it over writing our own.

datarhei Restreamer

Core trade-off: friendlier and broader, versus built for a narrower job.

  • Pick Restreamer if you want a setup wizard, a built-in player or public page for viewers, hardware encoding (Raspberry Pi, NVIDIA, Intel), or to run on ARM.
  • Pick Bunryu for a Linux server that forwards many pipelines to many destinations through long events, where per-output recovery, a History with FFmpeg's last output or bonded SRT ingest matter.

Its built-in SRT server uses gosrt, not libsrt, and in our trial its interface did not suit many outputs (why we did not use it).

Both run one FFmpeg process per output, but Bunryu does more to keep outputs running and to explain their failures. This comes from reading Core's process supervisor (process/process.go, October 2026), not from a side-by-side test:

  • Retries. Core restarts a failed process after a fixed delay. Bunryu backs off from 1 s to 16 s with jitter, so outputs to a platform that blipped do not all reconnect in the same second, and an output whose input is down waits without spawning FFmpeg.
  • Stalls. Core kills a process whose FFmpeg progress stops. Bunryu does the same, and also restarts an output whose destination socket is half closed while FFmpeg still reports progress, a case seen on YouTube.
  • Limits. Core can kill a process above a CPU or memory limit. Bunryu enforces memory only: a CPU limit would kill encodes that are merely busy on a loaded host.
  • Evidence. Both keep FFmpeg's last output per run. Bunryu also keeps a History per output and writes timestamped diagnostics for every start, exit, restart and watchdog action, and groups FFmpeg's repeated timestamp warnings.

SRS

Core trade-off: SRS is Bunryu's ingest, and its own forwarding is static.

Bunryu runs on official SRS for RTMP and SRT ingest. For outputs it does not use SRS's forward: in 6.0 a destination cannot be added or removed on a live stream without disconnecting the publisher, and a forward runs inside the SRS process, so a fault there can affect every stream. See the design decision.

Use SRS alone for a media server with a fixed configuration, or when you need WebRTC, HLS or its other delivery protocols. Bunryu adds the management layer around it for restreaming.

MediaMTX

Core trade-off: a flexible protocol router, versus FFmpeg's maturity on damaged input.

  • We tested MediaMTX in two roles and kept FFmpeg in both. As an SRT-to-RTMP converter it closed RTMP readers under 5-10% packet loss where FFmpeg stayed connected (details). As a forwarding hub for copy outputs it used about 10x less RAM but about 1.5x more CPU than FFmpeg, and FFmpeg would still be needed for transcodes, SRT destinations (details).
  • Its SRT is gosrt, like Restreamer's built-in server, not libsrt. We measured its conversion, not its SRT ingest on its own.
  • Pick MediaMTX for protocol conversion, WebRTC or RTSP, recording, running on Windows or macOS, or a single small binary. It is not a restreaming manager, so you set up and watch each forward yourself.

Paid products and hosted services

A paid product such as Wowza, or a hosted service such as Restream.io, means less to build or no server to run, and comes with support. Bunryu is for teams that want to run the server themselves: on their own infrastructure, with their own destinations and logs, with capacity set by their own hardware. It does not remove the work of operating a server; see sizing and reliability. We have not compared features or prices with these products.

When not to use Bunryu

  • You need a native ARM or Apple Silicon deployment, or a Windows or macOS host. Bunryu installs on Debian or Ubuntu x86_64 and the Docker image is x86_64 only.
  • You need hardware encoding. Bunryu's video encodings are CPU profiles, and most outputs are meant to copy the stream.
  • You want a public page or embeddable player for viewers. Bunryu forwards streams to destinations; it does not serve viewers.
  • You need WebRTC, RTSP or HLS delivery, or protocol conversion as a service.
  • You need more than the tested capacity: 50 inputs and 500 outputs.
